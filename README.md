## 二、测试范围

沿用「聚焦核心模块、打通主业务链」的策略，覆盖 4 个核心模块 + 报表核对：

```
① 基础资料 ──→ ② 商品管理
                    ↓
             ③ 采购管理（买进来）→ 库存增加 → 应付账款
                    ↓
             ④ 销售管理（卖出去）→ 库存减少 → 应收账款
                    ↓
             ⑤ 报表核对（库存 / 往来对账 / 销售统计）
```

**不在本轮范围**：零售管理、仓库管理（调拨/组装/拆卸）、财务（转账/预付款/多账户）、
权限矩阵（已设计 44 条用例但未执行）、报表其余 10 张。
未覆盖部分已在测试报告中按风险等级列出并给出补测建议。

## 三、测试方法与策略

### 3.1 用例设计方法

| 方法 | 应用 |
|---|---|
| **等价类划分** | 输入划分有效/无效等价类 |
| **边界值分析** | **依据真实字段类型反推**（`varchar(20)` → 测 19/20/21；`decimal(24,6)` → 测 6 位小数） |
| **场景法** | 采购订单 → 部分入库 → 余量入库 → 订单完成 |
| **状态迁移** | 单据状态机与库存/应付的联动（未审核/已审核/反审核） |
| **交叉核对法** | 每次操作后核对 ①库存数量 ②单据金额 ③单据状态 ④报表汇总 |
| **配置驱动** | 同一操作在 `force_approval_flag=0/1` 下预期不同，分别验证 |

### 3.2 执行分层

| 层次 | 方式 | 覆盖内容 |
|---|---|---|
| 第一层 | 手工（浏览器） | 提示文案、下拉联动、按钮权限、报表展示 |
| 第二层 | 手工 + 数据库 | 库存数量、应收应付、单据状态 |
| 第三层 | 接口自动化 | 字段校验、边界值、异常参数、CRUD 流程 |

### 3.3 缺陷发现手段

边界值探测 · 异常路径构造 · 跨接口联动验证 · 一致性对比 · 界面异常追查（抓包→日志→源码） · 数据库取证

## 四、接口自动化设计

### 4.1 集合结构（13 个文件夹 / 39 个请求）

| 文件夹 | 请求数 | 内容 |
|---|---|---|
| 01-认证 | 1 | 未授权访问必须被拒绝 |
| 02~06 五个模块 CRUD | 6 × 5 | 查询→新增→定位 id→修改→删除→确认（**请求链传递 id**） |
| 07-1~07-5 字段校验 | 5 | CSV 数据驱动，36 行数据 = 36 条用例 |
| 08-必填参数缺失 | 1 | 缺参数时的错误处理 |
| 09-单据接口 | 2 | 单据列表与状态筛选 |

### 4.2 关键实现

| 要素 | 方案 |
|---|---|
| **全参数化** | 所有请求体的值抽成变量（`{{depotName}}`、`{{customerType}}` 等），环境变量提供默认值 |
| **请求链** | 「3 查询并保存 id」在 Tests 里写 `pm.environment.set("depotId", id)`，后续修改/删除用 `{{depotId}}` |
| **数据驱动** | CSV 每行含 `caseId / 入参 / expectCode / desc`，一行即一条用例 |
| **断言策略** | 以「业务规范应有的行为」为期望值，**失败项即缺陷证据**（两层断言：业务码 + HTTP 状态码） |
| **鉴权** | 登录需验证码，自建 helper 服务读取 Redis 验证码换 token，写入环境变量 |
| **数据隔离** | 每次运行前按名称前缀清理测试数据，保证用例可重复执行 |
| **报告** | newman + htmlextra 生成 13 份 HTML 报告 |

### 4.3 运行方式

```powershell
# 单模块执行（示例：仓库字段校验）
newman run jshERP-接口自动化.postman_collection.json `
  -e jshERP.postman_environment.json `
  -d data/data_warehouse.csv `
  --folder "07-1 仓库字段校验（CSV）" `
  --delay-request 1500 `
  -r cli,htmlextra --reporter-htmlextra-export 报告_仓库校验.html
```

> `--delay-request 1500` 是为规避被测系统的防重复提交机制（缺陷 #17）。

**Postman 2026 版把 data files 移入付费版，因此批量执行统一走 Newman（官方 CLI，免费）。**
Postman GUI 用于调试单个请求，Newman 用于批量执行与出报告。

## 五、发现的缺陷（10 个）

| 编号 | 模块 | 缺陷 | 级别 |
|---|---|---|---|
| #9 | 基础资料-仓库 | 名称为空时查重接口缺 `name` 参数，抛异常返回「未知异常」 | 一般 |
| #10 | 基础资料-仓库 | 名称超 20 字符报「数据写入异常」（前端 max=30 与数据库 varchar(20) 不一致） | 一般 |
| **#11** | 基础资料-仓库 | **后端无服务端校验，绕过前端可写入空名称、1 字符名称** | **严重** |
| #12 | 基础资料-仓库 | 仓库停用后单据界面下拉未自动失效，需手动刷新 | 一般 |
| **#13** | 财务-结算账户 | **新建账户余额 NPE 被吞，导致整批账户余额停止实时计算** | **严重** |
| #14 | 系统管理-部门 | 部门编号无唯一性校验，可创建重复编号 | 一般 |
| **#15** | 商品-多单位 | **换算率可为 0，按副单位出入库时基本数量被算成 0（库存静默归零）** | **严重** |
| #16 | 销售-销售出库 | 明细数量缺 >0 校验：数量 0 可保存并审核，负数靠金额间接拦截 | 一般 |
| **#17** | 系统管理-防重复 | **同用户同秒同模块二次操作被强制退出登录（并发下 54% 请求被踢）** | **严重** |
| #18 | 单据-列表查询 | `/depotHead/list` 缺 `search` 任一键或 `type`/`subType` 为空即报「数据查询异常」 | 一般 |

### 重点缺陷说明

**#13 账户余额 NPE（最严重）**
> 界面显示保存成功，但查库发现新建账户 `current_amount` 为 NULL。
> 读源码定位到 `AccountService.select()`：求和 Map 未预置 0 值，无流水账户 `map.get()` 返回 null，
> `null.add()` 触发 NPE；异常被外层 catch 吞掉、**循环中断**。
> **影响不只是新账户显示空白，而是所有账户的余额都停止实时计算**（实测差额 1729 元，
> 并造成一笔"货已入库、款未扣减、无应付"的账实不符）。

**#17 防重复提交误伤（证据最充分）**
> 接口自动化跑着跑着大面积 `loginOut`，规律是"前 2 次成功，第 3 次起全部失败"。
> 查 Redis 发现会话键存在但 `userId` 字段被删；反向搜索 `deleteObjectByUserAndIp` 命中
> `LogService:140`：同用户 + 同 IP + 同秒 + 同模块二次操作即销毁会话。
> **A/B 对照实验**：并发 10×5 无间隔 → 成功 46%；串行 10 次（1.6s 间隔）→ 成功 100%。
> 证明强制退出由请求频率触发，与系统稳定性无关。

## 七、测试结论

1. **核心业务链数据联动正确**：采购订单→入库→库存→应付、销售出库→库存→应收，
   库存/金额/状态/报表四处交叉核对全部一致，主流程可用。
2. **输入校验严重不足**：前端校验完备但服务端几乎无校验，存在绕过前端写入非法数据的风险（#11）。
3. **财务计算存在严重缺陷**（#13），表现为余额不刷新与账实不符，建议优先修复。
4. **防攻击机制误伤正常操作**（#17），并发场景下 54% 请求被踢，影响系统可用性。
5. **综合评估**：核心流程可用，但数据校验与财务计算需重点修复后方可上线生产。

## 八、环境搭建要点（可复现）

```powershell
# 1. 依赖：JDK8 / Maven / MySQL(或MariaDB) / Redis / Node14
# 2. 后端编译
mvn -s settings.xml -DskipTests clean package
# 3. 数据库导入（注意：jshERP 默认连接 127.0.0.1:3306 的实例）
mysql -h127.0.0.1 -uroot -p123456 < jsh_erp.sql
# 4. Redis（注意端口与密码要与 application.yml 一致）
redis-server --port 6380 --requirepass 1234abcd
# 5. 启动
java -Dfile.encoding=UTF-8 -jar jshERP.jar      # 后端 :9999
npm run serve                                    # 前端 :3000
```

**踩过的坑**：本机同时存在 MySQL 8.0 与禅道自带 MariaDB 10.4，两者都在 3306，
必须用 `127.0.0.1`（TCP）才能连到后端真正使用的 MariaDB。
